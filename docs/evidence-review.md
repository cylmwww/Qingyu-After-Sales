# 证据检查、答案审核与有限纠错

检查与纠错用于在业务任务中核对证据和候选答案，默认关闭。它们适用于只读业务模式；原单轮 `/api/chat` 不进入这套独立审核。

前置检查关注作答所需事实与政策是否充分，后置审核检查已经生成的候选是否得到证据支持。审核模型是独立调用，不是多个自治 Agent 协商，也不能替代人工业务判断。

## 选择检查预设

文件位于 `configs/reviews/`：

| 文件 | 前置 / 后置 | 纠错方式 |
| --- | --- | --- |
| `off.v1.0.0.json` | 关 / 关 | 不启用检查与纠错。 |
| `checks-only.v1.0.0.json` | 开 / 开 | 检查，发现问题后按结果退出。 |
| `answer-only.v1.0.0.json` | 开 / 开 | 只用已有证据修改答案。 |
| `limited-correction.v1.0.0.json` | 开 / 开 | 允许定向补查或修改答案。 |
| `post-only.v1.0.0.json` | 关 / 开 | 后置审核与有限纠错。 |
| `pre-only.v1.0.0.json` | 开 / 关 | 前置检查与补查，最终答案未做后置审核。 |
| `loop-post-required.v1.0.0.json` | 关 / 开 | 配套复杂任务循环，不启用旧路径纠错。 |

普通业务任务可在“知识与配置”页选择 Agent 和审核预设后应用。定向补查应配合 `auto` 或 `dynamic`；锁定的 `fast`、`fixed` 与这类纠错不兼容。

服务默认配置也可写入 `.env`：

```dotenv
AGENT_CONFIG_PATH=configs/agents/dynamic.v1.1.0.json
REVIEW_CONFIG_PATH=configs/reviews/limited-correction.v1.0.0.json
```

```bash
docker compose up -d --force-recreate backend
```

已保存页面配置时应核对最终有效值。变更用于新任务，已有任务沿用原快照；非法组合在配置阶段拒绝。

## 检查过程

前置检查核对问题、必要事实、政策条件、时间与例外覆盖。后置审核结合程序检查和结构化模型输出，核对事实、政策适用、数值与引用支持；程序检查可以否决模型给出的“通过”。

审核输入包括问题、必要事实、证据和候选，不把生成过程的猜测当作依据。审核问题保留代码、关联结论、证据引用、详情及补查、修改、澄清或人工建议。

启用后置审核时，生成结果先保存为候选。普通对话事件只展示进度，通过发布检查后才显示最终答案。候选和修复稿可在受保护的追踪详情中核查，不能当作已经交付的回答。

## 修复范围与出口

仅修改答案可以修正措辞或已有证据的使用方式，不能填补需要新材料的缺口。定向补查复用原只读工具、规划和权限检查。默认最多两轮修复，可在新版本配置中下调。

| 结果 | 对使用者的含义 |
| --- | --- |
| `passed` | 当前启用的检查通过；是否有后置审核应看 `reviewed`。 |
| `repaired` | 有限修复后通过当前启用的检查。 |
| `clarification` | 等待用户确认必要事实。 |
| `partial_answer` | 普通任务路径仅给出已有确定性退款工具支持的已知预估，并说明其余未知。 |
| `handoff` | 提供交接说明，不表示已创建工单或人工已经接手。 |
| `failed` | 技术异常、协议问题、超时或额度不足，不能当作审核通过。 |

未启用纠错也不会直接发布被审核否决的候选。仅开启前置检查不表示最终答案经过后置审核。复杂循环的出口与普通路径有所不同，见[复杂任务循环](workbench.md#复杂任务循环)。

## 预算与恢复

检查默认输出上限为 1200 tokens、超时 30 秒，单轮问题数量有界；修复默认输出上限同为 1200。它们还受[任务共享预算](agent-and-sessions.md#持久化与预算)约束。

检查、生成、修复与补查都占用模型、工具、时间和 token 额度。进入纠错或显式恢复不会重置任务累计预算；无余额时应受控结束，不能通过反复恢复绕过限制。配置修改应新增 `id + version`。

## 查看审核详情

客服页展示当前前置、后置与纠错开关；追踪详情展示候选、程序与模型发现的问题、修复前后、新证据、轮次、耗时、预算和失败原因。真实调用、模拟审核与未审核结果应按实际记录区分。

真实模型可能遗漏问题、给出不合法引用或产生不完整输出。协议、引用和发布绑定校验失败时，候选不会发布；接口故障也不会自动降级为模拟审核。

审核通过只表示当前检查接受了该候选，不等于真实售后裁定正确。项目尚未完成完整人工业务语义验收，也没有对所有复杂纠错路径给出稳定效果保证。
