# 示例数据规范

本规范说明青屿售后的示例知识、模拟业务记录和案例标注如何组织，供阅读数据、维护内容和核对证据时使用。店铺、客户、订单与政策均为虚构。

它描述文件契约，不代替数据库表结构、HTTP 接口或真实商家政策。应用如何检索和调用业务工具，分别见[索引管理](index-management.md)与[业务说明](agent-and-sessions.md)。

## 数据入口

| 路径 | 内容 |
| --- | --- |
| `data/manifest.json` | 数据包文件清单、知识集合、业务快照与审核元数据。 |
| `data/schemas/` | 政策、FAQ、业务、案例、夹具和权限约束的 JSON Schema。 |
| `data/knowledge/policies/` | 含结构化元数据与条款锚点的 Markdown 政策。 |
| `data/knowledge/faq.json` | 引用具体政策规则的 FAQ。 |
| `data/business/seed.json` | 客户、商品、订单、支付、物流、售后、退款与快照。 |
| `data/system/constraints.json` | 只读、身份与证据可见性约束。 |
| `data/evaluation/` | 示例问题、预期结论与静态授权标注。 |
| `data/fixtures/` | 与正常知识分离的冲突、提示注入和超时夹具。 |

[数据清单](../data/manifest.json)由程序读取。其 `stage`、`scope` 和数据包版本描述该文件集合，不能当作整个应用的功能开关或版本号；例如 `model_api_calls=false` 表示数据包本身不调用模型，不表示应用没有模型接口。

## 身份、版本和引用

实体以 `(kind, id, version)` 精确标识。稳定 ID 使用大写字母、数字与连字符，版本为 `major.minor.patch`；同一实体的历史版本可以并存，同类型同版本不能重复。

规则继承所属政策版本。引用必须固定版本，例如：

```json
{"kind": "policy_rule", "id": "RULE-SHIP-001", "version": "1.0.0"}
```

常见引用类型包括政策、规则、FAQ、客户、商品、订单、订单行、支付、物流、售后、退款、快照与用户轮次；完整枚举以 Schema 为准。

数据包版本、Schema 版本、政策版本、知识集合、业务快照和索引 UUID 各有用途。分块与向量索引另外保存原文位置和配置契约，不应混称为同一个版本。

`review_status` 表示内容审核状态，`lifecycle` 表示文件生命周期，数据库索引的默认选择又是另一层状态。`approved` 需要与数据包的 `review_record` 一致；校验器不自动批准待审核内容。审核来源、日期和范围保存在清单中，内容实质变化需要重新核对。

## 时间语义

时间使用带时区 RFC3339，例如 `2026-10-09T10:00:00+08:00`。示例店铺使用 `Asia/Shanghai`；比较时按实际时刻处理。

| 字段 | 含义 |
| --- | --- |
| `effective_from`、`effective_until` | 生效区间，左闭右开；结束为 `null` 表示未设置终止。 |
| `selection_event` | 选择政策版本所依据的购买或售后申请事件。 |
| `purchased_at`、`paid_at` | 购买与支付时刻。 |
| `signed_at`、`applied_at` | 签收与售后申请时刻，用于窗口判断。 |
| `approved_at`、`initiated_at`、`settled_at` | 审批、发起退款与实际到账时刻。 |
| `observed_at` | 该版本业务记录的观察时刻。 |
| `captured_at` | 业务快照捕获时刻。 |
| 案例轮次 `at`、上下文 `evaluated_at` | 案例中的时间，不是真实模型运行时间。 |

示例无理由窗口为签收后连续 7 × 24 小时，边界相等包含在内；已核实质量问题的正常窗口为 30 × 24 小时。购买时间不能替代签收时间，时间满足也不等于其他退货条件全部满足。

政策按各自声明的事件选择。旧购买、新签收的订单仍可能适用旧运费版本；退款状态则应结合具体观察快照。不能把后轮输入、未来快照或未来到账记录提前提供给首轮。

## 政策与 FAQ

每份政策包含 JSON 元数据注释与人类可读正文。元数据包括 ID、版本、店铺、品类、生效区间、版本选择事件、来源、审核和规则；完整字段见 `data/schemas/policy.schema.json`。

规则包括 `conditions`、`effects`、`exceptions`、`related_refs`，正文具有与规则 ID 一致的唯一锚点，例如 `<a id="RULE-GEN-001"></a>`。

条件列表按 AND 解释。空列表不表示忽略品类、时间或正文例外。结构化字段只承载可核验的部分条件与参数，不能当作完整的自动售后裁定引擎。

FAQ 保存问题、改写、答案、适用范围和精确政策引用。数值参数应与引用条款一致；涉及不同时间选择事件的证据，通过 `evidence_time_bindings` 分别声明。FAQ 不覆盖政策，语义相似也不证明条件满足。

`quality_status=reported` 表示用户报告，`confirmed` 只能来自已核实记录。来源分别标记为虚构政策、模拟种子、用户输入或不可信夹具，不能相互替代。

## 金额、商品单元与退款

货币为 CNY，金额统一使用非负整数“分”。未知审批、到账金额用 `null`，不能用 0 代替未知。

订单级优惠先按商品优惠后的权重分摊，使用最大余数法处理余分；同一行多件商品再分配到从 1 开始的稳定单元序号。`unit_paid_amounts_cents` 保存冻结实付，部分退货时不重新分摊剩余商品优惠。

赠品实付为零，关联主商品退货时需要结合返还情况判断；缺赠品不能直接按宣传价扣款。原出库运费与退件运费分别解释，不能作为同一笔金额重复扣除。

例如 `ORD-006` 的两个付费行冻结为 15819 分和 6981 分，赠品为 0；`ORD-007` 的三个单元实付为 `[3000, 3000, 2999]` 分。这些是数据与算术示例，不表示申请符合退款资格或已经到账。

## 记录关联与快照

订单行、支付、物流、售后和退款都应能回溯所属订单；赠品关联必须指向同订单的非赠品行。同一快照对稳定实体只选择一个版本，保留在文件里的历史修订不等于当前全部可用。

待审批、待核验状态不产生已批准退款结果；`processing` 的到账金额与时刻为空，`settled` 需要对应的实际金额和时刻。无退款记录不能推断无售后，接口超时也不能解释成无记录。

基础快照与刷新快照是静态样例。应用按服务端配置选择快照，不等于已经接入实时订单同步或自动退款状态刷新。

## 案例标注与证据可见性

案例保存问题或多轮对话、可信上下文、快照、必要证据、预期结论、允许动作与禁止错误。预期助手输出是标注，不能作为用户事实或模型真实回答。

必要证据采用组间 AND、组内 `any_of` 为 OR；不同必需组不能随意互换。结论与证据标记各自可用轮次，用户修正只使明确字段的旧值失效；订单切换不沿用旧订单范围。

`visibility=assistant` 表示授权执行路径可以取得的材料，不表示初始输入拥有全部业务种子；`evaluator_only` 仅供后台核对，不能传入助手上下文。`authorization_results.json` 是静态标注，不是实际工具执行结果。

多跳依赖通过前序输出与后续输入绑定表达。并列读取多个政策不自动等于依赖式多跳。案例只允许只读查询、预估、澄清、拒绝越权或交接说明，不包含真实交易动作。

## 夹具、校验与维护

夹具必须声明 `is_test_fixture=true`、类型、描述、基础快照、操作和预期错误，正常政策、FAQ 与业务种子不能引用它们。提示注入中的文本属于不可信数据；超时不能转换为零退款、已到账或无记录。

数据维护时先更新精确版本与引用，再执行：

```bash
python -B scripts/validate_stage1.py
```

校验器核对 Schema 字段、身份与引用、条款锚点、生效区间、部分规则冲突、支付分摊、快照关联、案例时序及夹具隔离。它不证明全部自然语言规则、模型回答或真实业务效果正确；详细输出与错误处理见[数据校验](data-validation.md)。
